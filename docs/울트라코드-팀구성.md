# 울트라코드 에이전트 팀 구성 기준

Claude Code에서 울트라코드(워크플로)나 하위 에이전트를 쓸 때, 모델과 추론 수준을 어떻게 고르고 팀을 어떻게 짜는지 정리한 운영 기준입니다. 이 런처를 만들 때 쓴 기준을 그대로 옮겼습니다.

## 울트라코드·워크플로·하위 에이전트의 모델과 추론 수준

울트라코드가 켜져 있어도 아래를 따른다. 근거는 Anthropic 공식 자료(2026-11-19 조사, 출처 대조 완료)다. [번호]가 붙은 문장은 공식 자료, **(규칙)** 표시는 사용자와 정한 운영 규칙이다.

목표는 가장 싼 조합이 아니라 일에 가장 맞는 조합이다. 과한 것도 모자란 것도 틀리다. 모델과 추론 수준은 따로 정한다. 모델은 일의 종류로, 추론 수준은 그 일의 난이도로 고른다.

- 에이전트를 띄울 때는 호출마다 모델(`model`)과 추론 수준(`effort`)을 반드시 적는다. 적지 않아 세션 모델을 그대로 물려받게 두지 않는다.

### 1. 에이전트를 쓸지부터 정한다
- 가장 단순한 방법으로 시작하고, 모자랄 때만 복잡하게 만든다. [1]
- 여러 에이전트는 채팅보다 토큰을 약 15배 쓴다(에이전트 하나는 약 4배). 서로 독립적인 여러 방향을 동시에 살펴야 할 때 맞다. [2]
- 일이 앞 단계 결과에 기대는 사슬이거나, 한 컨텍스트에 들어가고 비용이 길게 늘어지지 않으면, 나눠 맡기지 말고 이 세션이 직접 한다. 공식 측정(이전 모델 기준)에서 나눠 맡겨 이득이 난 경우는 둘이다. 한 컨텍스트에 다 안 들어가는 일, 쉬운 일감인데 비용 꼬리가 긴 일. [3]
- 하위 에이전트는 더 똑똑한 답을 주지 않는다. 이득은 병렬 처리와 독립된 시각이다. [4] 자주 주고받아야 하는 일은 이 세션에서 한다. [5]

### 2. 모델 고르기: 일의 종류
| 모델 | 공식 자료가 말하는 맞는 일 | 맞지 않는 일 |
|---|---|---|
| Haiku 5.5 | 대량·빨라야 하는 일, 분류·추출·분배, 요약, 범위가 좁은 하위 에이전트 일(파일 모으기, 링크 점검) [6][7][4] | 복잡한 에이전트 코딩(Sonnet·Opus가 낫다) [7]. 요청이 10만 토큰을 넘으면 입력·출력 모두 단가가 5배가 되므로 큰 자료를 통째로 넣는 일 [6][3] |
| Sonnet 5.5 | 범위가 분명한 일상 일: 버그 수정, 코드 만들기, 문서·표 작성, 자료 분석, 대량 작업. 팀원 기본값으로 공식 권장 [8][9][10] | 오래 판단을 이어 가야 하는 열린 일(Opus가 확실히 강하다) [8] |
| Opus 5.5 | 대부분 일의 출발점. 긴 에이전트 코딩·지식 작업, 큰 이전·감사, 복잡한 설계와 여러 단계 추론 [11][12][10] | **(규칙)** 범위가 분명한 단순 반복은 아래 모델로 충분하면 쓰지 않는다 |
| Fable 5.2 | 가장 높은 능력. Opus를 xhigh·max까지 올려도 모자라면 Fable로 올린다 [11] | **(규칙)** 하위 에이전트에 쓰지 않는다. 사용자가 말했거나 Opus가 실패한 그 한 건에만 쓴다 |

- 모델을 바꾸는 것보다 추론 수준을 조정하는 쪽이 대개 더 나은 수단이다. [11] 그래서 **(규칙)** 순서는 이렇다.
  1. 일의 종류로 모델을 정한다.
  2. 난이도로 추론 수준을 정한다.
  3. 결과가 모자라면 그 건만 추론 수준을 한 단계 올린다. 그래도 안 되면 모델을 한 단계 올린다.
- 참고 수치(공식 내부 측정, 방향만 볼 것) [3]
  - Opus 5.5(medium)에 Haiku 하위 에이전트를 붙이면 비용 약 32%↓, 통과율 약 4%p↓. 추론 수준을 낮추는 것과 비슷한 대안이지 더 낫지는 않다.
  - 한 컨텍스트를 넘는 큰 결함 찾기에서 Opus 총괄 + Sonnet 하위 에이전트는 Opus 단독보다 약 1/3 쌌고 점수는 비슷했다.
- **(규칙)** "기능이 좋으니까"는 이유가 아니다. 아래 모델이나 낮은 수준으로 왜 안 되는지 말할 수 있을 때만 올린다.

### 3. 추론 수준 고르기: 그 일의 난이도
Claude Code에서 네 모델의 기본값은 medium이다(API 기본값은 Sonnet·Fable이 high로 다르다). 같은 이름의 수준이라도 모델마다 실제 강도는 다르다. [13]

| 수준 | 공식 자료가 말하는 쓸 때 | 주의 |
|---|---|---|
| low | 결과를 하나하나 확인하며 빨리 주고받는 일(브레인스토밍, 초안, 이름 바꾸기 같은 작은 변경) [13] | 토큰을 크게 아끼지만 능력이 다소 줄어든다 [14] |
| medium | 범위가 분명한 일상 일 [13] | 기본값 |
| high | 검증이 중요하거나 예외 경우가 많은 일(예: 기존 코드 버그 고치기), 복잡한 추론, 어려운 코딩·에이전트 일 [13][14] | |
| xhigh | 30분 넘게 걸리는 긴 에이전트·코딩 일 [14] | Sonnet은 xhigh·max에서 스스로 검토를 여러 번 돌려 시간·토큰이 더 든다 [3]. Opus는 xhigh가 high보다 점수 약 +1.4에 비용 2.5배였다 [3]. **(규칙)** Sonnet·Haiku는 high로 모자라면 쓴다. Opus는 거의 쓰지 않는다 |
| max | 사람 없이 풀게 할 어려운 문제 [13] | 효과가 점점 줄고 과하게 생각하는 경향이 있다 [13]. Sonnet은 한 평가(FrontierCode)에서 max가 xhigh보다 낮았다 [8]. **(규칙)** 사용자가 말했거나 xhigh로 실패한 그 한 건에만 쓴다 |

- 생각하는 과정은 출력 토큰으로 계산된다. 출력 단가는 입력의 5배다. [15][16]
- API에서는 요청 사이에 추론 수준을 바꾸면 캐시가 깨질 수 있다. [15] **(규칙)** 그래서 한 대화 안에서는 되도록 바꾸지 않고, 일의 경계에서 바꾼다.
- 하위 에이전트가 이 세션과 다른 모델이면 추론 수준을 물려받지 않는다. [5] **(규칙)** 그래서 띄울 때마다 모델과 추론 수준을 둘 다 적는다.

### 4. 팀 짜기
- 규모: 단순 조사는 에이전트 1개, 비교는 2~4개, 복잡한 조사만 10개 이상. [2] 팀은 3~5명으로 시작한다. 집중한 3명이 흩어진 5명보다 나은 경우가 많다. [18]
- 모양: 총괄이 일을 나눠 주는 형태, 독립 부분을 동시에 하는 형태, 평가 기준이 분명할 때 만들기-평가 반복 형태 중에서 고른다. [1]
- 공식 예시는 총괄은 상위 모델, 일꾼은 Sonnet이다. [2][10]
- 검수는 그 결과를 만들지 않은 새 에이전트가 한다. [4]
- 지시에는 목표, 결과 형식, 볼 자료, 일의 경계를 반드시 넣는다. 결과는 짧게 받고, 긴 결과는 파일로 남기고 위치만 받는다. [2][5]
- 끝난 팀원은 바로 끝낸다. 켜져 있는 동안 계속 토큰을 쓴다. [10]
- 워크트리: 두 에이전트가 같은 파일을 고치면 덮어쓴다. 파일을 나눠 맡기고, 동시에 고쳐야 하면 각자 워크트리를 준다. [18][19] 모델·추론 수준은 위 기준 그대로 정한다.
- **(규칙)** 총괄(이 세션)의 모델과 추론 수준도 같은 기준으로 판단한다. 지금 일에 비해 과하거나 모자라면 바꾸자고 먼저 제안하고, 허락받은 뒤 바꾼다.

### 5. 띄우기 전 보고와 승인 (규칙)
- 띄우기 전에 직접 훑어 일감 목록을 만들고, 필요한 수만큼만 띄운다. 도구 몇 번이면 끝나는 일은 에이전트 없이 직접 한다.
- **띄우기 전에 반드시 사용자에게 보고하고 승인을 받는다.** 워크플로든 하위 에이전트든, 한 개든 여럿이든 같다. 승인 없이 띄우지 않는다. 보고에는 표로 아래를 담는다.
  - 역할마다: 하는 일, 인원, 모델, 추론 수준
  - 역할마다: 왜 이 모델이고 왜 이 추론 수준인지 (이유는 빠뜨리지 않는다)
  - 전체 에이전트 수와 대략의 규모
- 팀 구성 보고는 항상 보기 좋은 표 하나로 정리한다(사용자 지시, 2026-11-24). 열은 단계 | 하는 일 | 인원 | 모델 | 추론 수준 | 이유 순서로 두고, 한 줄에 한 역할을 쓴다. 표 아래에 전체 인원과 진행 순서를 한두 줄로 붙인다. 표 밖에 역할 설명을 길게 늘어놓지 않는다.
- 승인받은 구성에서 모델, 추론 수준, 인원을 바꿔야 하면 바꾸기 전에 이유와 함께 다시 보고하고 승인받는다.
- 한 번 받은 승인은 그 보고에 적은 일에만 쓴다. 다음 단계의 팀은 다시 보고한다.
- 검증은 한 건에 한 명이 기본이다. 틀리면 피해가 큰 것만 여러 명이 본다.
- 끝나면 쓴 에이전트 수와 모델을 한 줄로 보고한다.
